# 总验收：对比创作底座整改

## 结果

本轮没有继续扩展“选择两个模型、自动创建两本书并开跑”的旧原型，而是把需求收敛为 MuMuAINovel 原有底座上的三个清晰生命周期：普通持久化书籍副本、同一对象的多模型候选、未来可选的两本书只读阅读。

九个拆分任务均已完成并归档：既有能力审计、错误原型清理、正式章节生命周期、项目创作配置、流水线整改、章节状态检查点、候选重新接入、项目深复制、单副本 UI。

## 用户可见能力

- 从书架、书籍详情或流水线页一次创建一本独立副本。
- 可选择只复制设定并从头写，或继承至后端证明可靠的第 X 章。
- 继承模式整体复制 1～X 章正文、正式分析、记忆、伏笔和该章人物/关系/组织/职业状态；X 后只留章节骨架。
- 副本复制项目自己的章节模型、分析模型、Skill、风格、MCP 策略和推进参数选择，但不复制 API Key 或插件凭据。
- 副本创建后进入自己的空闲流水线，由用户检查配置后手动启动；不自动生成、不一次创建两本。
- 单章节和分析多模型候选采用后重新进入正式落库/分析物化链路，不再丢失记忆、伏笔和实体状态更新。
- 流水线实际使用项目配置，并在上一章正式分析完成后才推进下一章。

## 已明确不做

- 原 `clone-for-compare` 的不完整静态复制 API 已被可靠检查点和深复制服务替代。
- 原 `compare-ui` 的双副本自动启动方案已被单副本、手动启动流程替代。
- 原 `compare-view` 的两本书并排阅读不属于本轮；未来确认真实需求后重新立项，并保持只读且不触发生成。

## 仍需记住的边界

AI 服务、Skill、MCP 插件和部分写作风格定义仍是用户级共享资源。书籍副本复制的是每本书自己的选择和运行快照；用户若在全局资源管理页直接修改同一资源定义，仍可能影响引用它的多本书。界面和后续设计不能把这种全局修改误称为“只修改当前书”。

前端生产构建仍提示已有的大包体积警告，但不影响本轮功能正确性；代码分包应作为独立性能任务处理，不能夹带进本轮架构整改。
