# 异步任务跟踪指南（Async Task Tracking）

> 状态：已生效（2026-08-10）
> 来源：本仓库 8 次生产事故复盘（分析卡 100%、任务跟丢、状态机漏状态）

## 核心原则

**原则 1：触发必跟踪。** 任何异步操作（分析/生成/展开/重写）被触发后，必须有且只有一个前端轮询在跟踪它。没有跟踪 = 任务完成无人知晓 = 用户看到"卡住"。

**原则 2：轮询停止条件必须覆盖状态机的全部终态。** 少一个终态 = 该状态下的任务永远在轮询列表里（无限请求），或永远显示假进度。

**原则 3：状态枚举前后端必须一致。** 后端新增/重命名任务状态时，前端类型定义与轮询条件必须同步更新（本次事故：`superseded` 状态后端已有，前端 3 处类型缺失）。

## 检查清单（写代码前过一遍）

### 触发方
- [ ] 触发接口返回后，前端是否**立即**查询任务状态并启动轮询？（不要用 `setTimeout` 延迟触发再不管——延迟窗口内的查询会查到旧任务）
- [ ] 触发与查询之间的时序：新任务是否已在库里？（后端应在**同事务**创建任务并先 commit，再通知前端完成）
- [ ] 应用内容/生成完成后的**自动分析**：显式"先 POST 触发 → 再查询轮询"，不要"setTimeout 触发后无人跟踪"

### 轮询方
- [ ] 停止条件覆盖**全部**终态（用排除法：`if (!运行中状态.includes(status)) 停止`）
- [ ] 有超时保护（防止后端任务永久卡死导致无限轮询）
- [ ] 轮询回调里**更新任务状态 UI**（进度条/状态标签），完成后展示结果或自动弹回结果界面
- [ ] 失败/被取代（superseded）有明确提示，且**从轮询列表移除**

### 状态机
- [ ] 新状态加入时：后端模型注释、前端类型（`types/index.ts`、组件内联类型）、所有轮询停止条件、进度条渲染分支，四处同步
- [ ] 数据库查询任务状态时按 `created_at DESC` 取最新一条

## 本次事故速查

| 症状 | 根因模式 | 修复要点 |
|---|---|---|
| 弹窗卡 100% 不动 | 查到 superseded/旧任务，不触发轮询，新任务无人跟踪 | 应用内容→显式触发+轮询；superseded 视为终态 |
| 无限轮询（每 2 秒请求） | 停止条件漏了 superseded | 停止条件用排除法 |
| 分析完成无通知 | 后台触发的任务没有加入轮询列表 | 完成回调里 `loadAnalysisTasks()`/`startPollingTask()` |

## 进阶模式：执行链自动接管（优于"提交时拦截"）

批量生成遇到"前章分析未就绪"时，比"提交时 409 拦截、让用户手动处理"更好的方案：

- **提交时不拦截**（用户一键发起，不用先满足前置）
- **执行链逐章自动接管**：分析失败/缺失/内容变更 → 自动重新分析（同步等待成功）；进行中 → 轮询等待（限时）
- **兜底**：超时/重析失败 → 明确错误终止 + 提示"勾选跳过"选项
- 实现要点：等待循环用 `timed_out` 标志区分"超时退出"与"完成/失败/消失退出"（后者应落入重析分支，不可误报超时）；`db.expire_all()` 刷新会话后重新查询；限时必须有（10 分钟）

适用判断：用户一键操作期望"尽量自动完成"的场景（批量生成/卷内生成）用自动接管；需要用户决策的场景（如覆盖写）才用提交时拦截。
