# 技术设计：对比创作底座整改

## 设计目标

本次不是新增一套“对比写书系统”，而是让不同模型创作的书继续使用同一套 MuMuAINovel 正式创作底座。新增能力只负责：复制一本普通书、保存这本书自己的创作配置、选择可靠继承节点。

## 架构不变量

1. 一本副本就是一个普通项目，不是候选结果或浏览器临时状态。
2. 正式正文只有一个落库入口；正式分析结果只有一个物化入口。
3. 第 N+1 章开始前，第 N 章当前正文对应的分析必须完成。
4. 项目数据深复制；用户级密钥、插件连接和资源目录不复制。
5. 只有有证据可重建的章节状态才能成为继承节点。
6. 任一阶段失败后，不能留下可见的半本副本或继续消耗后续模型额度。

## 核心模块

### 正式章节生命周期模块

负责正文版本检查、正式落库、项目字数、生成历史、派生状态失效、分析任务创建和等待策略。普通生成、批量生成、流水线、章节候选采用都通过它写入正式正文。

### 标准分析物化模块

接收已经解析并校验的结构化分析，统一处理剧情分析、向量记忆、伏笔、角色、关系、组织、职业和任务状态。调用者不能跳过其中某项副作用。

### 项目创作配置模块

项目保存自己的默认选择：章节模型、分析模型、Skill、风格、MCP 策略和参数。AI 服务密钥、MCP 连接、Skill/风格资源定义继续是用户级资源。每次运行冻结必要的名称、版本和提示词内容。

### 章节状态检查点模块

每章标准分析完成后保存该时刻的实体状态快照，并绑定正文内容摘要、分析任务和章节。修改较早正文会使该章及后续检查点失效。旧书只补登记最新可证明一致的连续分析节点。

### 项目深复制模块

输入为源项目、复制模式和可选检查点；输出为一个全新的普通项目。模块负责所有 ID、外键、JSON 引用重映射、向量集合重建、补偿清理和最终完整性报告。

## 配置所有权

| 数据 | 所有者 | 副本策略 |
| --- | --- | --- |
| 正文、分析、记忆、伏笔、角色、关系、组织、职业 | 项目 | 深复制并重映射 ID |
| 项目默认创作选择与流水线参数 | 项目 | 深复制配置值 |
| AI 服务/API Key | 用户 | 只引用服务 ID，不复制密钥 |
| MCP 连接及凭据 | 用户 | 只复制项目使用策略，不复制凭据 |
| Skill、写作风格定义 | 用户或全局 | 复制选择；运行记录冻结版本/内容摘要 |
| 后台任务、运行锁、未采用候选 | 运行历史 | 默认不复制 |

## 状态检查点方案

采用“每章实体状态快照 + 章节关联数据按范围复制”：

- 检查点保存角色、关系、组织、组织成员和职业的完整当前状态；
- 正文、PlotAnalysis、StoryMemory、Foreshadow、GenerationHistory 继续保存在原有关系表中，克隆时按章节范围选择；
- 检查点记录正文内容摘要和分析任务，防止正文变化后继续使用旧状态；
- Chroma 记忆不共享集合，克隆时在新项目集合中重新写入。

相较从不完整日志逆推，这个方案更容易证明正确；代价是增加存储量，但小说项目的实体规模可控。

## 兼容与上线

- 旧项目不伪造历史检查点，只提供最新可靠节点；
- 新表同时提供 PostgreSQL 和 SQLite 迁移；
- 先禁用不完整的分析候选采用，再在状态重建能力完成后恢复；
- 旧双副本自动运行入口先删除，不做兼容跳转；
- 项目级并排阅读不在本轮范围。

## 任务依赖

`原型清理` → `章节生命周期` → `配置所有权` → `流水线整改` → `状态检查点` → `候选重新接入` → `项目深复制` → `单副本 UI` → `总体验收`。

已完成的既有功能审计为所有任务提供事实基线，不参与业务实现。
