# AI 功能二开边界指南

## 核心原则

新增 AI 功能首先要回答“它是否只是已有 MUMUAINovel 工作流的新入口或新配置”，只有现有能力无法表达时才新增服务、状态机或数据模型。

## 先确认生命周期

把功能分成两类并明确写入 PRD：

- **持久化项目**：有项目 ID、书架入口、数据库状态、流水线、可暂停/继续/导出/删除，刷新页面后仍存在。
- **临时候选**：属于某个章节/大纲/分析任务，有输入快照、候选结果、重试和采用动作，采用前不修改正式内容。

不能用“临时对比页”替代持久化项目，也不能把候选结果直接写进正式章节。

## 复用底座检查清单

开发前必须逐项核对：

- 现有项目、章节、流水线和后台任务的生命周期；
- 现有模型路由、Skill、写作风格和 MCP 参数；
- 正文生成后的分析任务、记忆、伏笔、角色、关系和组织状态更新；
- 现有候选比较的快照、持久化和采用机制；
- 暂停、失败、重试、回滚和权限检查。

如果新功能绕开其中任何一项，必须在 PRD 中说明原因并增加等价验收，不能默认为“后续再补”。

## 设计反模式

- 为了体现“二开”而新建一套并行生成服务；
- UI 一次性编排多个后台副作用，却没有持久化来源、进度和重试边界；
- 复制静态设定时遗漏职业、风格或关联表；
- 让流水线使用与手动生成不同的 Skill、上下文或分析契约；
- 把“创建两个临时结果”和“创建一个可管理项目”混称为“对比”。

## 复盘要求

每个跨层 AI 功能完成后记录：复用了哪些底座、哪些地方不得不扩展、扩展是否改变了正式数据生命周期、失败时如何恢复。若答案不清楚，功能仍处于设计阶段，不应进入实现。

## 副本独立性

项目副本不是引用或视图。任何被复制的可写数据都必须拥有新的主键，并把所有外键重映射到副本内的数据。对于“继承至第 X 章”，第 1～X 章的正文和过程数据必须一同复制；否则第 X+1 章的上下文会引用不存在或属于源书的状态。验收必须包含：修改 A 项目的正文、分析、角色、关系、组织、职业和配置后，源项目与 B 项目均保持不变。

源书已经推进超过 X 时，角色、关系、组织、职业、伏笔和记忆必须从第 X 章可靠状态检查点恢复，不能从源书当前表读取后再过滤章节。复制前先为整个闭包分配新 ID，再递归改写结构化 JSON 中“完全等于源 ID”的值；不要对正文或普通文本做全局字符串替换。

关系数据库与向量库无法共享一个原生事务时，新项目在 SQL 提交前不可见，向量写入失败要回滚 SQL 并删除目标 collection。PostgreSQL 是写入顺序的验收真相：没有 ORM relationship 的父子对象不能依赖一次 flush 自动排序，应明确按项目→大纲→章节、职业→角色→关联、组织→成员、分析任务→检查点分阶段 flush。

## 候选采用边界

比较候选只能保存冻结输入、模型输出和人工选择状态，不能自行拼装正式章节、分析或项目状态。采用适配器必须把选中结果交给普通入口使用的正式落库或分析物化模块，确保历史记录、分析任务、记忆、伏笔、角色、关系、组织、职业和状态检查点遵循同一套规则。

“采用”标记必须与正式状态写入处于同一数据库事务：正式写入失败时回滚，批次仍可重试；重复采用同一候选必须幂等。若采用成功后还要调度事务外后台任务，服务应明确返回“本次是否首次采用”，接口只能在首次采用时调度，避免快速双击造成重复模型调用。

正式分析使用项目自己的分析模型、MCP 和插件配置，不得默认沿用生成候选所用的模型。批量候选必须明确为各章独立预览，未采用、未完成正式分析的候选不能作为后续章节上下文，也不能被描述为连续创作。
